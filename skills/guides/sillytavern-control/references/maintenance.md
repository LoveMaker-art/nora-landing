# 维护与恢复

## 诊断

从 `st.doctor`、`st.config_locations` 和对应资源的最小读取开始。区分 MCP 启动失败、HTTP／认证失败、目标不存在、参数不支持、磁盘写入失败、需要刷新及实际运行失败；不统称网络问题。

`st.plan_change` 可描述计划，不等于执行；`st.verify` 只证明资源能够读取。日志可能包含聊天、路径或凭据，读取与对外反馈都按当前问题的最小范围脱敏。

## 快照与恢复

写入工具返回 `snapshotId` 时记录它；必要时可先用 `st.snapshot(label=...)` 创建明确基线。快照包含配置、用户数据及部分插件路径，属于私有备份，不放进共享技能包。

恢复前查清快照清单和覆盖范围。0.12.0 的回滚会还原快照中已有的整条路径，可能连同之后其他合法修改一起回退；记录为原本不存在的路径会跳过，并非一律清除后来新建的内容。不要把它说成只撤回刚才一个字段。

用户已明确授权恢复相应范围后，调用：

```json
{"id":"<实际快照编号>","confirm":true}
```

这是 `st.rollback` 的参数。恢复前避免活动页面或服务继续并行写入；需要停服时先说明影响并取得对应授权。完成后读取受影响角色、聊天、世界书和配置，检查保留项与需要的刷新／重启。不凭 `ok: true` 宣称一切恢复正常。

## 失败重试

明确拒绝且未执行的请求，可在修正授权、参数或目标后重试。网络超时、断开或返回内容无法解释时，先读目标确认真实变化。世界书新建、消息追加、插件安装均不盲目重复；同名冲突不默认覆盖。

失败涉及服务端代码、自动脚本或模型请求时，文件快照不保证撤销外部请求、计费或远端副作用。说明能核验的范围，不承诺全部撤销。

## 运行控制

`st.runtime.control` 的 `status`、`start`、`stop`、`restart` 依赖部署者配置的命令。命令缺失时说明未接入；命令退出成功后仍需检查 HTTP 与用户所需服务。用户只要求改一项设置时，不自动重启整个酒馆。

普通酒馆控制不调用 `st.source.write`、`st.dev.run`、`st.plugin.scaffold` 或 `st.index.refresh` 变更源码、生成程序或运行任意开发命令。用户另行提出开发任务时重新确定范围。
